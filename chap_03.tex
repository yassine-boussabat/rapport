\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

\paragraph{}This chapter covers the first sprint of the project, which lasted two weeks and focused entirely on
discovery and data model mapping. Before any line of generation code could be written, a thorough
understanding of the Longview data model was required: the entities that make up a valid test
dataset, the buffer tables that back them in SQL Server, the stored procedures used to load them,
the order in which they must be populated, and the field-level constraints and business rules that
govern each record. This chapter presents the sprint backlog, the results of the data model
analysis, a detailed description of each entity and its key attributes as reflected in the implemented
Data Transfer Objects (DTOs), and the class diagram that captures all entities and their
relationships.

\section{Longview Pre-BCP Buffer Mechanism}
% ─────────────────────────────────────────────

\paragraph{}Longview uses a \textbf{pre-BCP (Bulk Copy Program) buffer} loading mechanism to ingest test data into
its SQL Server database. Instead of inserting records directly into the platform's live tables, data is
first written into a set of dedicated staging tables, referred to as pre-BCP buffer tables. Once all
buffer tables are populated, a set of stored procedures validates the records, enforces cross-table
business rules, and transfers the data into the live schema in the correct dependency order.

\paragraph{}This mechanism has two important implications for the data generator. First, the generator must
produce INSERT statements targeting the buffer tables, not the live tables. Second, it must respect
a strict population order: a buffer table that depends on another through a foreign key or a stored
procedure input parameter cannot be populated before the table it depends on. The discovery
phase mapped this order explicitly across all buffer tables, and each entity's TypeScript DTO was
designed to mirror the exact column set of its corresponding buffer table.

\section{Entity Discovery and Description}
% ─────────────────────────────────────────────

\paragraph{}The analysis of the existing SQL scripts and the Longview schema documentation identified seven
primary entity domains. Each domain groups one or more buffer tables and corresponds to a distinct
financial concept in the Longview data model. The following sections describe each entity, its role
in the data model, and its key attributes as they appear in the corresponding TypeScript DTO classes
implemented in the generator module.

% ─────────────────────────────────────────────
\subsection{Account Group and Account Hierarchy}
% ─────────────────────────────────────────────

\paragraph{}An \textbf{Account Group} is a logical container that groups one or more investment accounts under a
named label. It is the top-level entity in the account hierarchy. In the Longview buffer model,
the account group record is identified by a \textbf{client\_account\_group\_name} and is associated to a
representative account through a \textbf{client\_account\_id} reference. Optional attributes include a
\textbf{client\_principal\_currency\_code} for the group's base currency and aggregate valuation fields
\textbf{net\_asset\_value} and \textbf{total\_asset\_value}. Account groups have no financial attributes of their
own beyond these aggregates; they exist purely to structure the account tree.

\paragraph{}The \textbf{Account Hierarchy} entity captures the parent-child relationships between accounts and
account groups. Each hierarchy record links a child account to its parent group, establishing the
nesting structure required by the Longview portfolio management layer. The hierarchy buffer table
must be populated after both the account group and account buffer tables, as it holds foreign key
references to both.

\paragraph{}Key attributes of the \texttt{AccountGroupDto} class include:

\begin{itemize}
    \item \textbf{client\_account\_group\_name} (\texttt{string}, required): Human-readable name that uniquely identifies the account group within the system.
    \item \textbf{client\_account\_id} (\texttt{string}, required): Reference to the representative account associated with the group.
    \item \textbf{client\_source\_system\_id} (\texttt{string}, optional): Identifier of the originating source system, used for traceability in multi-system environments.
    \item \textbf{client\_principal\_currency\_code} (\texttt{string}, optional): ISO 4217 currency code of the group's principal currency.
    \item \textbf{net\_asset\_value} (\texttt{string}, optional): Aggregate net asset value of all accounts in the group.
    \item \textbf{total\_asset\_value} (\texttt{string}, optional): Aggregate total asset value of all accounts in the group.
\end{itemize}

% ─────────────────────────────────────────────
\subsection{Account}
% ─────────────────────────────────────────────

\paragraph{}An \textbf{Account} represents an investment portfolio or client mandate. It is one of the most central
entities in the Longview data model because virtually every other entity -- orders, executions,
positions, and model allocations -- is anchored to one or more accounts through a
\textbf{client\_account\_id} reference. The \texttt{AccountDto} class mirrors the full column set of the account
buffer table, distinguishing a small set of mandatory fields from a large set of optional
configuration and user-defined fields.

\paragraph{}Key required attributes of the \texttt{AccountDto} class include:

\begin{itemize}
    \item \textbf{client\_account\_id} (\texttt{string}, required): Unique alphanumeric identifier of the account, used as a foreign key throughout the schema.
    \item \textbf{short\_name} (\texttt{string}, required): Abbreviated label for the account, used in display and reporting contexts.
    \item \textbf{name\_1} (\texttt{string}, required): Primary full descriptive name of the account or portfolio.
    \item \textbf{client\_currency\_code} (\texttt{string}, required): ISO 4217 base currency code of the account (e.g., \texttt{USD}, \texttt{EUR}).
\end{itemize}

\paragraph{}Notable optional attributes include \textbf{client\_manager\_code} (portfolio manager reference),
\textbf{inception\allowbreak\_date} (mandate start date), \textbf{client\_default\_model\_name} (default allocation model),
\textbf{client\_tax\_lot\_relief\allowbreak\_method} (tax lot relief strategy), \textbf{equity\_market\_value} and
\textbf{fixinc\_market\_value} (pre-loaded valuation figures), and up to sixteen \textbf{user\_field} and
\textbf{user\_id} extensibility slots that accommodate client-specific metadata without schema changes.

% ─────────────────────────────────────────────
\subsection{Model and Model Objective}
% ─────────────────────────────────────────────

\paragraph{}A \textbf{Model} defines a target allocation strategy used by the portfolio management layer of Longview.
It specifies how a portfolio should be invested across asset classes or individual securities. Models
are referenced by accounts through the \textbf{client\_default\_model\_name} field and drive automatic
order generation to bring portfolios into alignment with their target weights.

\paragraph{}A \textbf{Model Objective} record links a model to a specific target security and defines the target
weight or allocation rule for that position within the model. Multiple model objectives can be
attached to a single model, one per target security or asset class. The model service generates both
the parent model record and its associated objective records as a single coherent unit.

% ─────────────────────────────────────────────
\subsection{Security}
% ─────────────────────────────────────────────

\paragraph{}A \textbf{Security} represents a tradeable financial instrument. It is the most structurally complex entity
in the Longview data model because the platform supports several distinct asset classes, each with
its own dedicated DTO class and buffer table. The discovery phase identified six security subtypes
implemented in the generator: equities (\texttt{EquitySecurityDto}), generic instruments
(\texttt{GenericSecurityDto}), fixed income securities (\texttt{FixedIncomeSecurityDto}), options
(\texttt{OptionSecurityDto}), \allowbreak futures (\texttt{FutureSecurityDto}), and FX forwards
(\texttt{FxForwardSecurityDto}).

\paragraph{}All equity and generic security subtypes share a common set of base attributes. The required
fields of the \texttt{EquitySecurityDto} class are:

\begin{itemize}
    \item \textbf{client\_security\_id} (\texttt{string}, required): Unique identifier of the security, used as a foreign key in orders, executions, prices, and positions.
    \item \textbf{symbol} (\texttt{string}, required): Market ticker symbol of the instrument.
    \item \textbf{security\_name\_1} (\texttt{string}, required): Primary descriptive name of the security.
    \item \textbf{security\_type\_code} (\texttt{string}, required): Asset class and instrument type classification code.
    \item \textbf{pricing\_factor} (\texttt{number}, required): Multiplier applied to raw prices to derive market values.
    \item \textbf{income\_factor} (\texttt{number}, required): Multiplier applied to income calculations.
    \item \textbf{client\_principal\_currency\_code} (\texttt{string}, required): ISO 4217 currency code of the security's principal denomination.
    \item \textbf{client\_income\_currency\_code} (\texttt{string}, required): ISO 4217 currency code used for income distributions.
    \item \textbf{client\_country\_code} (\texttt{string}, required): ISO country code of the security's domicile.
\end{itemize}

\paragraph{}\textbf{Fixed income securities} (\texttt{FixedIncomeSecurityDto}) carry a richer set of required
fields reflecting their additional complexity: beyond the base identifiers and factors, they require
\textbf{issuer\_type\_code}, \textbf{principal\_payment\_type\_code}, \textbf{income\_payment\_type\_code},
\textbf{payment\_frequency}, and \textbf{accrued\_interest\_day\_count}. Optional fields govern the coupon
and redemption schedule (\textbf{coupon\_rate}, \textbf{maturity\_date}, \textbf{dated\_date},
\textbf{redemption\_date}, \textbf{redemption\_value}), floating rate characteristics
(\textbf{client\_bp\_ratevariable\_flag}, \textbf{rate\_reset\_frequency\_code}, \textbf{spread\_over\_index\_rate},
\textbf{cap\_rate}, \textbf{floor\_rate}), prepayment model parameters, and convertibility flags. Child
schedule records (call schedules, put schedules, coupon schedules, convertible schedules) are
stored in dedicated extension buffer tables populated after the parent fixed income record.

\paragraph{}\textbf{Derivatives} -- represented by \texttt{OptionSecurityDto} and \texttt{FutureSecurityDto} --
additionally require an underlying security reference, an expiration date, a strike price (for
options), and a contract size multiplier. \textbf{FX forwards} (\texttt{FxForwardSecurityDto}) require the
forward settlement date, the nominal amount, and the two leg currency codes.

% ─────────────────────────────────────────────
\subsection{Price}
% ─────────────────────────────────────────────

\paragraph{}A \textbf{Price} record stores the market price of a security on a given date. The Longview pricing
layer requires at least one price record per security to allow the system to compute portfolio
valuations and validate order quantities. The \texttt{PriceDto} class links each price record to its
security through the \textbf{client\_security\_id} foreign key and carries the pricing date and the
closing price. Price records must be generated after the security records they reference.

% ─────────────────────────────────────────────
\subsection{Order}
% ─────────────────────────────────────────────

\paragraph{}A \textbf{Proposed Order} (modelled by \texttt{ProposedOrderDto}) is a buy or sell instruction issued by a
portfolio manager for a specific account and security. Orders are the primary drivers of the trade
lifecycle in Longview. The required fields are \textbf{client\_account\_id}, \textbf{client\_security\_id},
\textbf{side\_mnemonic} (trade direction), and \textbf{proposed\_value} (the target notional amount or
quantity). Optional fields cover execution constraints such as \textbf{limit\_type},
\textbf{limit\_price\_1}, \textbf{time\_in\_force}, \textbf{settlement\_date}, and \textbf{delivery\_date}, as well
as routing attributes (\textbf{client\_broker\_id}, \textbf{client\_trader\allowbreak\_id}), and strategy metadata
(\textbf{strategy\_mnemonic}). Up to thirty-two \textbf{user\_field} slots accommodate client-specific
extensions.

\paragraph{}The simpler \texttt{OrderDto} class models a group-level or block order record. Its required fields
are \textbf{client\_account\_id}, \textbf{client\_security\_id}, \textbf{order\_quantity} (\texttt{number}), and
\textbf{order\_side\_code}. Optional fields include \textbf{order\_status\_code}, \textbf{limit\_price},
\textbf{order\_type\_code}, \textbf{order\_date}, and \textbf{settlement\_date}. Group orders must be generated
before the proposed orders they contain.

% ─────────────────────────────────────────────
\subsection{Execution}
% ─────────────────────────────────────────────

\paragraph{}An \textbf{Execution} record (modelled by \texttt{ExecutionDto}) represents the trade confirmation
produced when a proposed order or part of it is filled in the market. The required fields are
\textbf{client\_security\_id}, \textbf{client\_side\_code} (trade direction at execution), \textbf{quantity}
(filled quantity), \textbf{average\_price} (execution price), and \textbf{client\_exec\_broker\_id}
(the executing broker). Optional fields provide full settlement and cost breakdown: \textbf{client\_account\_id},
\textbf{trade\_date}, \textbf{settlement\_date}, \textbf{client\_comm\_broker\_id}, \textbf{commission\_rate},
\textbf{client\_settlement\_currency}, \textbf{settlement\_fx\_rate}, \textbf{local\_commission},
\textbf{sec\_fee}, \textbf{taxes}, \textbf{stamp\_tax}, and \textbf{other\_charges}. Up to thirty-two
\textbf{block\_user\_field} extensibility slots are also available. Execution records must be generated
after the proposed order records they fill.

% ─────────────────────────────────────────────
\subsection{Position (Tax Lot)}
% ─────────────────────────────────────────────

\paragraph{}A \textbf{Position} record (modelled by \texttt{PositionDto}) represents the current inventory holding
of a specific security within a specific account, stored as a tax lot in the Longview schema. The
only strictly required fields are \textbf{client\_account\_id} and \textbf{client\_security\_id}, which
together identify the holding. The full set of optional attributes covers the economic substance of
the lot: \textbf{trade\_date\_qty} (current quantity held), \textbf{trade\_date} (acquisition date),
\textbf{cost} (total acquisition cost), \textbf{cost\_base} (base-currency cost), \textbf{unit\_cost\_base}
(per-unit cost), \textbf{settlement\_date}, and \textbf{accrued\_income\_local}. Additional optional fields
support analytics: \textbf{delta}, \textbf{macaulay\_duration}, \textbf{modified\_duration},
\textbf{implied\_volatility}, and \textbf{principal\_factor}. FX-related positions carry
\textbf{client\_purchased\_currency\_code}, \textbf{client\_sold\allowbreak\_currency\_code}, and the corresponding
traded volumes. Positions must be generated after all executions for the relevant account-security
pair have been recorded.

\section{Table Population Order}
% ─────────────────────────────────────────────

\paragraph{}One of the most important outputs of the discovery phase was the determination of the strict
population order that must be respected when generating the SQL INSERT statements. Because the
pre-BCP buffer tables are linked through foreign key relationships and because the Longview stored
procedures validate inter-table consistency before transferring data to the live schema, any
violation of this order causes the entire load to fail.

\paragraph{}Table~\ref{tab:population-order} presents the discovered population order for the pre-BCP buffer
tables, grouped by entity domain.

\section{Entity Class Diagram}
% ─────────────────────────────────────────────

\paragraph{}Figure~\ref{fig:class-diagram} presents the UML class diagram of the Longview data model as
discovered during Sprint 1. The diagram shows all primary entities involved in test data generation,
their key attributes and types as reflected in the implemented DTO classes, and the relationships
and multiplicities between them. This diagram served as the primary reference specification for all
generation services implemented in the subsequent sprints.

\begin{figure}[h!]
\centering
%\includegraphics[width=1.0\textwidth]{img/class-diagram.png}
\caption{UML class diagram of the Longview entities targeted by the test data generator}
\label{fig:class-diagram}
\end{figure}

\paragraph{}The relationships captured in the diagram reflect the following structural rules discovered during
the sprint:

\begin{itemize}
    \item An \textbf{AccountGroup} is associated with one or more \textbf{Accounts} through the AccountHierarchy link, using \textbf{client\_account\_group\_name} and \textbf{client\_account\_id} as the join keys.
    \item A \textbf{Model} contains one or more \textbf{ModelObjective} records (\texttt{1} to \texttt{1..*}), each targeting a specific security identified by its \textbf{client\_security\_id}.
    \item A \textbf{Security} is specialized into one of six subtypes: \textbf{EquitySecurity}, \textbf{GenericSecurity}, \textbf{FixedIncomeSecurity}, \textbf{OptionSecurity}, \textbf{FutureSecurity}, or \textbf{FxForwardSecurity}, each implemented as a distinct DTO class.
    \item A \textbf{FixedIncomeSecurity} may have zero or more associated \textbf{CallSchedule}, \textbf{PutSchedule}, \textbf{CouponSchedule}, and \textbf{ConvertibleSchedule} child records stored in dedicated extension buffer tables.
    \item A \textbf{Security} has one or more associated \textbf{Price} records (\texttt{1} to \texttt{1..*}), linked through \textbf{client\_security\_id}.
    \item A \textbf{GroupOrder} aggregates one or more \textbf{ProposedOrders} (\texttt{1} to \texttt{1..*}).
    \item A \textbf{ProposedOrder} is linked to exactly one \textbf{Account} via \textbf{client\_account\_id} and one \textbf{Security} via \textbf{client\_security\_id}.
    \item An \textbf{Execution} is linked to a \textbf{ProposedOrder} (identified by \textbf{client\_security\_id} and \textbf{client\_account\_id} matching), and its \textbf{quantity} must not exceed the remaining unfilled quantity of the parent order.
    \item A \textbf{Position} (TaxLot) is identified by the combination of \textbf{client\_account\_id} and \textbf{client\_security\_id}, and its \textbf{trade\_date\_qty} is derived from the net sum of execution quantities for that account-security pair.
\end{itemize}

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
% ─────────────────────────────────────────────

\paragraph{}This chapter presented the results of Sprint 1, the discovery and data model mapping phase.
By analyzing the existing SQL scripts, the pre-BCP buffer table schema, and the stored procedures
used by the Longview loading pipeline, the complete set of entities required for test data generation
was identified and documented. For each entity -- account groups, accounts, models, securities
(across six distinct subtypes), prices, orders, executions, and tax lot positions -- the exact field
names, their TypeScript types, their required or optional status, and their business rule constraints
were recorded and formalized into the DTO classes that constitute the data contract of the
generator module. The strict population order across the twenty buffer tables was established, and
the relationships between all entities were formalized in the UML class diagram presented in
Figure~\ref{fig:class-diagram}. This foundation gave the implementation of Sprint 2 a precise and
verified specification to work from. The following chapter presents Sprint 2, which covers the
core generation engine and the standalone mode of the system.
