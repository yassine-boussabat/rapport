\chapter{Sprint 1 -- Discovery and Data Model Mapping}

% ---------------------------------------------------------
\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
% ---------------------------------------------------------

\paragraph{}This chapter presents the first sprint of the project, which spanned two weeks. Its purpose was not to
implement the generator yet, but to build the financial and technical understanding needed before
implementation. Since the application produces data for Longview, the analysis first moved from a
computer science view of the problem to a finance-aware view: what is an account, what is a
security, why orders and executions are different, and how positions represent what an account
already owns.

\paragraph{}The chapter is therefore written as a progressive discovery story. It begins with the
sprint backlog, then explains how the analysis of Longview extracts, manually prepared SQL files,
and QA team feedback led to the selection of the most important entities to generate. After that,
the chapter presents the discovered relationships, the Longview pre-BCP loading mechanism, the
technical population order, and finally the class diagrams used as the reference for implementation.

\section{From Extract Analysis to Target Entities}
% ---------------------------------------------------------

\paragraph{}Longview provides many extract files, and at the beginning of the sprint it was not
realistic or useful to generate all of them. The first discovery work was therefore to understand
which extracts were actually important for QA scenarios. To do this, the existing
extract files, the SQL scripts that were generated manually by the team, and the recurring data
needs expressed during discussions with QA engineers were analyzed.

\paragraph{}This analysis showed that the generator had to focus on the entities that form the
core portfolio and trading workflow. These entities were selected because they are frequently
needed in tests, because they are connected by strong dependencies, and because generating them
manually is time-consuming and error-prone. The selected scope covers accounts and account
groups, models, securities, prices, hierarchy rows, positions, proposed orders, orders, and
executions.

\paragraph{}For a reader coming from computer science, these extracts become easier to
understand when they are read as a business workflow rather than as isolated files. Longview
manages client portfolios. Each portfolio belongs to an account structure, holds financial
instruments, receives market prices, and can generate trading activity. The generator had to
reproduce this story with valid test data.

\paragraph{}At a simplified level, the workflow is the following:

\begin{enumerate}
    \item \textbf{Portfolio structure:} accounts and account groups define where holdings and trades belong.
    \item \textbf{Investment definition:} models describe target allocations that may guide how an account should be invested.
    \item \textbf{Market universe:} securities define the instruments that can be priced, classified, held, or traded.
    \item \textbf{Current holdings:} positions describe what each account already owns.
    \item \textbf{Trading activity:} proposed orders, orders, and executions describe the intention to trade, the trading instruction, and the market fill.
\end{enumerate}

\paragraph{}This business sequence became the first mental model for the application. It helped
identify which objects had to be generated first and which identifiers had to be shared between
services. For example, an order cannot be meaningful without an existing account and security.
Similarly, a sell order is safer when the application knows the account's current position, because
the generated scenario should not sell an impossible quantity.

\section{Discovered Entities and Relationships}
% ---------------------------------------------------------

\paragraph{}After selecting the target extracts, the next step was to describe the relationships
between their entities. The goal was to keep only the relationships that influence valid data
generation: mandatory references, optional references that must be valid when supplied, and
implementation rules used by the application.

\paragraph{}The most important discovery was that the generated values are not independent. A
price is only valid if it refers to an existing security. A position is only valid if it connects an
existing account to an existing security. Proposed orders and orders also depend on valid
account-security pairs, and sell-side scenarios must be coherent with the positions already held by
the account.

\paragraph{}Some relationships are direct extract constraints, while others are generation rules
added to keep the scenario realistic. For example, an option must reference an underlying security,
and an execution generated by the application is produced from an equity order even when the
extract itself mainly validates the security and account references. These links explain why the
generator had to share identifiers between services instead of producing each file separately.

\paragraph{}This relationship mapping became the basis for the DTO design and for the later
generation pipeline. Each service had to know which upstream identifiers were already available,
which optional references could be left empty, and which references had to be preserved to make
the final dataset load correctly in Longview.

\section{Longview Pre-BCP Loading Mechanism}
% ---------------------------------------------------------

\paragraph{}Once the target entities and their relationships were clear, the next question was how
Longview expects this data to be loaded. Longview does not insert the generated records directly
into its live business tables. Instead, data is first inserted into pre-BCP buffer tables. These
staging tables receive the raw records, then Longview stored procedures validate them, apply
business rules, and transfer the accepted data into the live schema.

\paragraph{}This mechanism shaped the generator in two important ways. First, the generated SQL
had to target the buffer tables, not the final Longview tables. Second, the output script had to
respect a strict population order. If a row references an account, a security, a model, or a
classification level, that referenced data must already exist in Longview or be loaded earlier in
the same generated scenario.

\paragraph{}For this reason, Sprint 1 linked each selected business entity to its extract file, its
DTO representation, its buffer table, and the stored procedure order used during loading. This is
the point where the finance workflow becomes a technical dependency graph.

both views: it creates a coherent business scenario while emitting SQL in the order accepted by
the pre-BCP pipeline.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
% ---------------------------------------------------------

\paragraph{}This chapter presented Sprint 1 as the discovery phase that allowed the project to
enter the Longview finance domain before implementing the application. The main result was a
clear mapping between financial concepts, DTOs, pre-BCP buffer tables, and dependency rules.

\paragraph{}By understanding accounts, securities, prices, positions, orders, and executions as
connected parts of the same workflow, the generator could be designed around valid relationships
instead of isolated random records. This foundation gave Sprint 2 the specification needed to
build the standalone generation engine and produce SQL scripts that respect Longview's loading
constraints.
