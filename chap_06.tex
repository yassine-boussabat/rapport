\chapter{Sprint 4 -- LLM Integration and Realistic Data Enrichment}


% ─────────────────────────────────────────────
\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
% ─────────────────────────────────────────────


\paragraph{}This chapter presents Sprint 4, which spanned four weeks and was dedicated to the integration of a Large Language Model
enrichment layer into the test data generator. The generator implemented in the previous sprints
already produced structurally valid records, but many descriptive fields were still algorithmic:
security names, account names, model labels, issuer descriptions, and symbols followed deterministic
patterns. Sprint 4 aimed to improve the realism of these values while preserving the most important
constraint of the project: generation must remain reliable even when the external AI service is
unavailable.

\paragraph{}The implemented solution integrates the Google Gemini API through a dedicated
\texttt{LlmModule}. The LLM layer is optional, controlled through environment variables, and designed
as an enrichment step on top of already valid DTO objects. This means that the algorithmic generator
remains the source of truth for identifiers, relationships, quantities, dates, and business rules,
while the LLM improves only selected textual and descriptive fields.

\subsection{LLM Enrichment Architecture}

\paragraph{}The LLM integration follows a defensive enrichment architecture. The base generation services
first create complete and valid DTO arrays. These arrays are then passed to \texttt{LlmService}, which
decides whether enrichment is enabled and delegates the work to specialised enrichers. If the LLM
layer is disabled or fails, the original DTO arrays are returned unchanged.

\paragraph{}The main components of the integration are:

\begin{itemize}
    \item \textbf{\texttt{LlmClientService}:} low-level Gemini client wrapper responsible for API keys,
    model selection, queueing, rate-limit handling, and request execution.
    \item \textbf{\texttt{LlmService}:} facade used by the generator. It exposes methods such as
    \texttt{enrichSecurities()}, \texttt{enrichAccounts()}, \texttt{enrichModels()}, and
    \texttt{enrichAccountGroups()}.
    \item \textbf{Prompt builders:} functions that create structured prompts for each entity type and
    require JSON output.
    \item \textbf{Enrichers:} services that parse LLM output, apply field constraints, and merge safe
    enriched values back into the generated DTOs.
\end{itemize}

\paragraph{}Figure~\ref{fig:ch6-llm-sequence} presents the runtime sequence of the enrichment step. The
core generation services first produce a complete algorithmic dataset, then request enrichment from
\texttt{LlmService}. If LLM integration is disabled, the service immediately returns the original
dataset. If it is enabled, the corresponding entity enricher builds a structured prompt, calls the
LLM client, and waits for a JSON response from the external API.

\paragraph{}The sequence makes the fallback behavior explicit. A fully valid response is merged into all
items, a partial response enriches only the valid records while preserving the original values for
the rest, and an invalid or failed request is discarded. In all cases, the generation process
continues with a valid dataset, which protects SQL generation from external AI failures.

\subsection{Fallback Strategy}

\paragraph{}The LLM is treated as an optional quality improvement, not as a required dependency. The
fallback strategy has three levels. First, if \texttt{LLM\_ENABLED} is false or no API key is
configured, enrichment is skipped. Second, if a model or key fails, the client attempts another
configured route. Third, if all LLM attempts fail or return unusable data, the enricher returns the
algorithmically generated objects without modification.

\paragraph{}This approach protects the generation pipeline from external service instability. A QA engineer
can therefore continue generating valid SQL scripts even during API outages, quota exhaustion, or
invalid LLM responses.

\section{Implementation}
% ─────────────────────────────────────────────


\subsection{LLM Client Service}

\paragraph{}The \texttt{LlmClientService} wraps the \texttt{@google/generative-ai} SDK. At startup, it reads the
available API keys and creates one client per key. It then builds a model chain containing Gemini
2.5 Flash as the primary model, Gemini 2.5 Flash Lite as the overflow model, and optionally Gemini
2.5 Pro as a last-resort model when enabled by configuration.

\paragraph{}The service also implements a small request scheduler. Incoming prompts are placed in an
internal queue and processed according to \texttt{LLM\_MAX\_CONCURRENCY}. Each key tracks its own
in-flight requests and cooldown state per model. When a request fails because of a rate limit, the
corresponding key/model pair is put on cooldown, and the service tries another available route.
Denied-access errors disable the affected key for the rest of the run.

\subsection{Security Batch Enrichment}

\paragraph{}Security enrichment is implemented as a batch process because securities are the most numerous
records in the generated dataset. The \texttt{SecurityBatchEnricher} creates work items for equities,
fixed income securities, FX forwards, generics, futures, and options. These work items are split
into chunks according to \texttt{LLM\_SECURITY\_BATCH\_SIZE}, and each chunk is sent to the model with
a prompt requiring a JSON array response.

\paragraph{}After receiving the response, the enricher parses the JSON, verifies that every returned item has
the expected identifier and security kind, and applies only the fields that are safe for that
security subtype. For example, equities may receive improved \texttt{client\_security\_id},
\texttt{symbol}, and \texttt{security\_name\_1} values, while fixed income securities may receive a
better \texttt{security\_description}. Each accepted string is truncated using the field length
constraints so that it remains compatible with the target \texttt{.DAT} file.

\subsection{Account, Account Group, and Model Enrichment}

\paragraph{}Additional enrichers target account groups, accounts, and models. These services follow the
same defensive pattern: build a structured prompt, call the LLM client, parse JSON output, merge
only known fields, and report whether a fallback was used. The enrichers improve descriptive fields
such as account names, account group names, and model labels without changing numeric quantities,
foreign keys, or the generated dependency structure.

\subsection{Integration in the Generator}

\paragraph{}The \texttt{GeneratorService} integrates the enrichment layer after base generation and before
validation and file writing. Securities are generated first, then passed through
\texttt{llmService.enrichSecurities()}. Models, accounts, and account groups are enriched in the same
way. The validator still runs after enrichment, which means that LLM-provided values are subject to
the same checks as algorithmic values.

\paragraph{}This placement was chosen deliberately. If enrichment occurred before DTO creation, the LLM
would influence structural logic and could create invalid relationships. By enriching complete DTOs,
the system allows the LLM to improve realism while keeping referential integrity under the control
of deterministic code.

\subsection{Prompt and Response Constraints}

\paragraph{}Prompts are designed to request concise JSON responses rather than free-form text. The expected
response shape is different for each entity type, but all prompts share the same principle: each
returned item must be traceable to the original generated item through an identifier. The enrichers
reject responses with missing identifiers, wrong kinds, invalid arrays, or unexpected lengths.

\paragraph{}This strict parsing is important because LLMs can produce extra text, malformed JSON, or values
that do not match the requested schema. The implementation treats such output as unusable and falls
back to the original generated data instead of attempting unsafe corrections.

\paragraph{}The main difficulty of this sprint was balancing realism and reliability. The solution avoids
making the LLM responsible for business rules, quantities, or relationships. Instead, it uses the
LLM only as a controlled text-enrichment layer. This decision keeps the generator predictable while
still improving the readability and plausibility of generated financial records.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
% ─────────────────────────────────────────────


\paragraph{}This chapter presented Sprint 4, which integrated optional LLM enrichment into the Longview Test
Data Generator. A dedicated client service manages Gemini API calls, fallback models, multiple API
keys, queueing, concurrency, and rate-limit cooldowns. Entity-specific enrichers improve textual
and descriptive fields while preserving deterministic generation as the source of truth for data
structure and business consistency. The resulting system can generate more realistic datasets when
the LLM is available, but it remains fully operational when the LLM is disabled or unavailable. The
following chapter presents Sprint 5, which finalizes the application with the configuration library
and global report-level validation.
