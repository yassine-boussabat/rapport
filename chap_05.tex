\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

\paragraph{}Once the standalone mode was operational, Sprint 3 addressed a second QA use case: many
test scenarios do not start from an empty dataset. In practice, testers may need to reuse accounts
or securities that already exist in a Longview SQL Server environment, then generate only the
additional records required to complete a scenario.

\paragraph{}Sprint 3 addresses this need through the connected mode. This mode keeps the same generation objective as standalone mode,
but adds a controlled database preparation step before generation. The QA engineer can connect to
SQL Server, select existing Longview records, and use them as anchors for the generated SQL Server
loading script, while the application keeps database access read-only.

\section{Sprint Specification}

\paragraph{}The connected mode is organized around five workflow steps: connection, data grabbing,
configuration, preview, and generation. The last three steps reuse the standalone pipeline; the new
work of this sprint is to prepare a database-backed context before that pipeline is launched.

\section{Sprint Design}

\paragraph{}The design of Sprint 3 adds a database access layer before the standalone generation engine.
The frontend owns the five-step connected workflow and the connected-context guards. The backend
owns SQL Server access, controlled data retrieval, connected artifact preparation, and delegation to
the existing validation and SQL assembly pipeline.

\section{Realization}

\paragraph{}Connected mode was implemented as an extension of the standalone generation engine.
The same core generation, validation, loading order, and SQL script assembly are reused after the
connected context is prepared. The difference is that the generation is guided by the grabbed data:
existing accounts, account groups, or securities become the base of the output, and only the missing
complementary records are generated around them.

\subsection{Backend Reuse and Additions}

\paragraph{}The added backend work is limited to the connected layer. \texttt{DatabaseService} manages
SQL Server connection testing, session state, and controlled data reading. \texttt{ConnectedGeneratorService}
then receives the grabbed accounts, account groups, or securities, decides which complementary data
must still be generated according to that selection, and sends the prepared context to the shared
generation pipeline. The
connected database is used only as a read source; the final result remains a downloadable SQL script.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

\paragraph{}Sprint 3 delivered the connected-mode extension of the standalone generator. The application
can now connect to SQL Server, grab existing Longview records, prepare the connected input context,
and reuse the existing generation pipeline to download an ordered SQL Server loading script. This
mode adds realism without duplicating the generation logic already implemented in standalone mode.
