\chapter{Sprint 2 -- Core Generation Engine and Standalone Mode}


% ─────────────────────────────────────────────
\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
% ─────────────────────────────────────────────


\paragraph{}This chapter presents Sprint 2 of the project, which spanned two weeks and delivered the
core generation engine and the first fully operational mode of the test data generator: the
standalone mode. Building directly on the data model specification established in Sprint 1, this
sprint translated the DTO contracts and population order into a working NestJS backend capable
of generating syntactically and semantically valid SQL INSERT scripts for all twenty pre-BCP buffer
tables, without requiring any connection to a live Longview database. The chapter covers the sprint
backlog, the architectural design of the generation engine, a description of each generation service
and the SQL script builder, and the implementation results with a demonstration of the produced
output.

\subsection{Architecture of the Generation Engine}
% ─────────────────────────────────────────────


\paragraph{}The generation engine follows a layered, service-oriented architecture consistent with the NestJS
module system. All generation logic is encapsulated in the \texttt{GeneratorModule}, which declares
one injectable service per entity domain plus three cross-cutting services: the orchestrator
(\texttt{GeneratorService}), the SQL script builder (\texttt{SqlScriptGeneratorService}), and the
validator (\texttt{ValidatorService}). A separate \texttt{ConfigLibraryModule} provides the shared
constraints configuration to all generation services through NestJS dependency injection.

\paragraph{}The strict population order established in Sprint 1 is enforced at the script assembly level by
the orchestrator and SQL generator services. During generation, the orchestrator first prepares the
data pools needed by dependent services, then writes the resulting \texttt{.DAT} files and SQL
statements in the Longview loading order. This design ensures that dependent records such as
prices, orders, executions, and positions are built from valid upstream identifiers while the final
script remains aligned with the pre-BCP loading sequence.



% ─────────────────────────────────────────────
\subsection{Generation Request and Response Contract}
% ─────────────────────────────────────────────


\paragraph{}The frontend communicates with the backend through a single \texttt{POST /generate} endpoint.
The request body carries a \texttt{GenerateDto} object that specifies the quantities of each
entity type to generate (number of accounts, securities per subtype, orders, executions, and
positions) and optional configuration flags such as whether to include derivatives or fixed income
schedules. The response carries a \texttt{GenerationResultDto} containing the assembled SQL script
as a string and a statistics object summarising the number of INSERT statements produced per
entity domain.

\paragraph{}Figure~\ref{fig:sequence-diagram} presents the sequence diagram of the complete standalone
generation workflow. The diagram starts with local configuration and preview, then details the
generation request sent to the backend through \texttt{POST /generate-and-download}. In the success
scenario, the backend validates the request, invokes the core generation services, creates the
dataset, delegates SQL assembly to the script service, and returns \texttt{load\_test\_data.sql} to
the browser for download.

\paragraph{}The diagram also documents the failure paths handled by the interface. If dataset generation or
SQL creation fails, the backend returns an error response that is shown to the user. If the request
does not reach the server because of a network or server availability problem, the frontend reports
the failure without changing the locally stored configuration.

% ─────────────────────────────────────────────
\subsection{Constraints Configuration}
% ─────────────────────────────────────────────


\paragraph{}All enumerated domain values and valid code lists used across the generation services are
centralised in \texttt{constraints.ts}. This file exports typed constant arrays for ISO 4217
currency codes, ISO country codes, security type codes, order side mnemonics, settlement
currency codes, broker identifiers, and other categorical fields. By referencing this single source
of truth, every generation service picks values from the same validated set, guaranteeing that the
generated records satisfy the enumeration constraints enforced by the Longview loading procedures.


% ─────────────────────────────────────────────
\subsection{Entity Generation Services}
% ─────────────────────────────────────────────


\paragraph{}Each entity generation service is an injectable NestJS class that exposes a \texttt{generate()}
method. The method accepts the user's generation parameters and any upstream identifiers produced
by previously invoked services, and returns an array of populated DTO instances. The following
describes the key generation logic of each service.

\paragraph{}\textbf{AccountGroupService} generates the requested number of account group records. Each group
receives a unique \texttt{client\_account\_group\_name} composed of a realistic asset-class prefix
(e.g., \texttt{EQUITIES}, \texttt{FIXED\_INCOME}) concatenated with a zero-padded sequence number, a
randomly sampled \texttt{client\_principal\_currency\_code} drawn from the constraints list, and
optional aggregate valuation figures computed as random decimal values within a realistic range.

\paragraph{}\textbf{AccountService} generates one or more account records per account group, ensuring that
the \texttt{client\_account\_id} values produced are unique and that each account's
\texttt{client\_currency\_code} is consistent with its parent group's principal currency. The service
also populates optional manager codes, inception dates, and pre-loaded equity and fixed income
market values.

\paragraph{}\textbf{HierarchyService} produces the account hierarchy records that link each account to its
parent account group. Because this service depends on the outputs of both the account group and
account services, it receives both arrays as inputs and produces one hierarchy record per
account-group pairing.

\paragraph{}\textbf{ModelService} generates model records and their associated model objective records as a
single unit. Each model receives a unique name and contains one or more allocation rows based on
sector or portfolio level codes. The service supports equal, weighted, and random allocation modes,
then normalises the resulting target weights so that each model remains balanced and usable by the
Longview portfolio layer.

\paragraph{}\textbf{SecurityService} generates security records across all six supported subtypes in
dependency order: equities and generic securities first (no dependencies), followed by fixed income
securities and their optional child schedule records, and finally derivatives (options and futures,
which require an underlying security reference) and FX forwards. The service draws
\texttt{security\_type\_code}, currency, and country values from the constraints configuration and
computes realistic \texttt{pricing\_factor} and \texttt{income\_factor} values per asset class.

\paragraph{}\textbf{PriceService} generates one or more price records per security. Each price record carries
a \texttt{client\_security\_id} reference, a pricing date set to the generation date, and a closing
price derived from the security's asset class (equities receive prices in the 10--500 range; fixed
income securities receive prices near par value, i.e., in the 95--105 range; derivatives receive
prices scaled to their contract size).

\paragraph{}\textbf{OrderService} generates both group order records (\texttt{OrderDto}) and proposed order
records (\texttt{ProposedOrderDto}) in the correct dependency order. Group orders are generated
first and assigned a unique reference; proposed orders are then generated referencing valid account
and security identifiers from the upstream pools and linked to their parent group order.

\paragraph{}\textbf{ExecutionService} generates execution records for a subset of the proposed orders,
simulating a realistic partial-fill scenario in which some orders remain open. Each execution's
\texttt{quantity} is constrained to not exceed the parent order's \texttt{proposed\_value}, and the
\texttt{average\_price} is set to a value within a realistic spread of the security's last generated
price.

\paragraph{}\textbf{PositionService} derives position (tax lot) records from the net execution quantities
for each account-security pair. For each unique combination of \texttt{client\_account\_id} and
\texttt{client\_security\_id} appearing in the execution records, the service sums the filled
quantities and creates a position record whose \texttt{trade\_date\_qty} equals that net sum,
ensuring consistency between the execution layer and the position layer of the generated dataset.


% ─────────────────────────────────────────────
\subsection{SQL Script Generator Service}
% ─────────────────────────────────────────────


\paragraph{}The \texttt{SqlScriptGeneratorService} is responsible for converting the arrays of populated DTO
instances produced by the entity services into a single executable SQL script. For each DTO array,
the service iterates over the records in the established population order, constructs a
\texttt{INSERT INTO <buffer\_table> (\ldots) VALUES (\ldots)} statement for each record, handles
\texttt{NULL} for optional fields that were not populated, escapes single-quote characters in string
values, and formats numeric values without quotation marks. The assembled statements are grouped
by entity domain with section header comments to facilitate readability and manual inspection of
the generated script.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
% ─────────────────────────────────────────────


\paragraph{}This chapter presented Sprint 2, which delivered the complete standalone mode of the test
data generator. The core generation engine was implemented as a set of NestJS injectable services,
one per entity domain, orchestrated by a central \texttt{GeneratorService} that enforces the
twenty-step population order established in Sprint 1. A centralised constraints configuration
guarantees that all generated field values satisfy the enumeration and domain rules of the Longview
loading pipeline. The \texttt{SqlScriptGeneratorService} assembles the populated DTO arrays into
a single executable SQL script ready for direct use by the QA team. The three-step frontend
workflow guides the user from parameter configuration through pre-generation preview to result
download, providing a complete and self-contained generation experience. The standalone mode
requires no database connection, making it immediately deployable in any environment. The
following chapter presents Sprint 3, which extends the system with SQL Server database
connectivity and the connected mode of the generator.
