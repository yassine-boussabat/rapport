\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
% ─────────────────────────────────────────────


\paragraph{}After the discovery work carried out during Sprint 1, Sprint 2 transformed the mapped
Longview entities, relationships, and loading order into the first operational version of the
application. The objective was to implement a standalone mode capable of generating a coherent SQL
loading script without requiring any connection to a Longview database.

\paragraph{}This chapter presents the design and implementation of this standalone generation engine. It
describes the sprint backlog, the standalone use case, the main design views, the backend generation
pipeline, the frontend workflow, and the validation activities carried out at the end of the sprint.

\subsection{Backend Architecture View}
% ─────────────────────────────────────────────


\paragraph{}The generation engine is implemented in the NestJS \texttt{GeneratorModule}. It contains one
service per entity domain and three shared services: \texttt{GeneratorService},
\texttt{SqlScriptGeneratorService}, and \texttt{ValidatorService}.

\paragraph{}The orchestrator calls the services in dependency order. The SQL generator then emits the
validated DTO arrays according to the Longview pre-BCP loading sequence.

\subsection{Request and Response Contract}
% ─────────────────────────────────────────────


\paragraph{}The standalone frontend calls \texttt{POST /generate-and-download}. The request contains the
selected \texttt{GenerationParams}; the response is the generated \texttt{load\_test\_data.sql}
file. A log endpoint is used to display generation progress.

\paragraph{}If an error occurs during generation or validation, the backend returns a structured error
response instead of a downloadable file. This prevents invalid SQL output and allows the frontend to
display the failure state through the generation logs.

\section{Implementation}

\subsection{Configuration Inputs}

\paragraph{}After the design view, the next step is to describe the information provided by the QA
engineer before generation. The configuration tab is divided by entity domain. Each section maps to
\texttt{GenerationParams} and directly affects generated entity fields. Table~\ref{tab:standalone-config-model}
summarises this mapping.

\paragraph{}Although standalone mode lets the QA engineer choose which data domains to generate, the
configuration is constrained by dependency rules. Base data such as accounts and securities can be
selected from the configuration interface, but dependent data such as models, positions, proposed
orders, final orders, and executions requires both accounts and securities to be available. In
addition, executions can only be enabled when final orders are generated, because each execution
must be linked to an existing order. These rules prevent incoherent configurations before the
generation request is sent to the backend.

% ─────────────────────────────────────────────
\subsection{Backend Processing}
\paragraph{}This section explains what happens after the frontend sends the configuration to the
backend. The processing starts with shared constraints, continues with entity generation and
orchestration, then ends with validation and SQL script assembly.
% ─────────────────────────────────────────────


% ─────────────────────────────────────────────
\subsubsection{Constraints Configuration}
% ─────────────────────────────────────────────


\paragraph{}\texttt{constraints.ts} centralises the valid domain values used by the generator: currency
codes, country codes, security types, order sides, settlement currencies, brokers, and other
enumerations. All services reuse these lists to avoid invalid categorical values.


% ─────────────────────────────────────────────
\subsubsection{Internal Generation Algorithms}

\paragraph{}Standalone data is produced by backend algorithms, not by external input files. The services
use templates, sequences, constrained values, pseudo-random variation, and shared identifiers.

\paragraph{}The user configuration controls record counts, names, allocation modes, quantity ranges,
buy/sell ratios, and long/short ratios. Dependent records reuse generated identifiers: prices,
positions, and orders reference securities; account groups and orders reference accounts; options
reference underlyings; executions reference final orders.


% ---------------------------------------------------------
\subsubsection{Entity Generation Services}
% ─────────────────────────────────────────────


\paragraph{}Each entity service is a NestJS injectable class responsible for one Longview domain. Services
receive \texttt{GenerationParams} and required upstream DTO arrays, then return typed DTO arrays for
validation and SQL generation.

\paragraph{}The implemented services are:

\begin{itemize}[nosep]
    \item \textbf{SecurityService}: generates equities, fixed income instruments, FX forwards, generic securities, futures, options, and optional fixed-income schedules.
    \item \textbf{ModelService}: generates model allocations, model properties, and model-of-model links.
    \item \textbf{AccountService}: generates account master records from the configured count, currency, and naming pattern.
    \item \textbf{AccountGroupService}: derives account groups from generated accounts.
    \item \textbf{HierarchyService}: classifies generated securities using hierarchy and GICS values.
    \item \textbf{PriceService}: generates one price record per generated security.
    \item \textbf{PositionService}: generates holdings using accounts, securities, long/short ratios, quantity ranges, and optional tax-lot splitting.
    \item \textbf{OrderService}: generates proposed and final orders using accounts, securities, positions, side ratios, date ranges, and settlement rules.
    \item \textbf{ExecutionService}: generates execution rows from eligible final equity orders, including partial fills and settlement dates.
\end{itemize}


% ─────────────────────────────────────────────
\subsubsection{Generation Orchestrator Service}
% â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€


\paragraph{}\texttt{GeneratorService} orchestrates the standalone pipeline. It applies defaults,
normalises the reference date, records progress logs, calls entity services in dependency order,
then runs validation.

\paragraph{}The orchestrator preserves shared identifiers between domains. It coordinates generation only;
\texttt{SqlScriptGeneratorService} performs the DTO-to-SQL conversion.


% â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€
\subsubsection{Validator Service}
% â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€


\paragraph{}\texttt{ValidatorService} checks required fields, lengths, numeric values, flags, dates, and
identifier consistency before SQL assembly.

\paragraph{}It also checks references between domains: accounts, securities, model names, orders, and
executions must point to generated records. In addition, it verifies practical coherence rules, such as
matching execution quantities with their parent orders and keeping position quantities within the
configured ranges. Invalid data stops generation before download.


% â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€â”€
\subsubsection{SQL Script Generator Service}
% ─────────────────────────────────────────────


\paragraph{}\texttt{SqlScriptGeneratorService} converts validated DTO arrays into one executable SQL
script. It writes \texttt{INSERT} statements in population order, handles \texttt{NULL} values,
escapes strings, formats numeric fields, and groups statements by entity domain.


% ─────────────────────────────────────────────
\subsection{Frontend Workflow}

\paragraph{}The backend engine is exposed through a three-step frontend flow. The frontend uses React Router
with three routes:
\texttt{/standalone/configuration}, \texttt{/standalone/preview}, and
\texttt{/standalone/generation}. All routes are handled by the \texttt{StandaloneMode} component.

\paragraph{}The \texttt{StandaloneMode} page stores the configuration, maps it to the backend contract,
starts generation, polls progress logs, and displays the final download state.

\paragraph{}Sprint 2 delivered the standalone mode. The backend generates coherent DTO arrays using
entity services, validates them, and converts them into a SQL Server loading script. The frontend
provides configuration, preview, generation progress, and download. The next chapter presents
Sprint 3 and the connected mode.
