% ─────────────────────────────────────────────
\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
% ─────────────────────────────────────────────


\paragraph{}This chapter presents Sprint 5, the final two-week sprint of the project. After the standalone mode,
connected mode, and LLM enrichment were operational, the remaining objective was to improve
reusability and finalize the application experience. In practice, QA engineers often reuse the same
generation scenarios across regression cycles. Re-entering the same quantities, filters, and
generation options at every session would reduce the practical value of the tool. Sprint 5 therefore
introduced a configuration library that allows users to save, load, rename, search, filter, and
delete generation configurations.

\paragraph{}The sprint also covered final integration work: routing between modes, compatibility checks for
connected configurations, local frontend persistence, shared UI components, and final validation of
the end-to-end workflows. This chapter describes the sprint backlog, the design of the configuration
library, the backend and frontend implementation, and the validation performed before project
closure.

\subsection{Configuration Library Architecture}

\paragraph{}The configuration library is implemented as a local persistence layer inside the NestJS backend.
The \texttt{AppModule} configures TypeORM with the \texttt{better-sqlite3} driver and stores data in a
local \texttt{config-library.db} file. This choice keeps the feature lightweight: no external database
server is required, and the library can be created automatically when the backend starts.

\paragraph{}The library is grouped inside the \texttt{ConfigLibraryModule}, which contains:

\begin{itemize}
    \item \textbf{\texttt{SavedConfig}:} the TypeORM entity representing one saved configuration.
    \item \textbf{\texttt{ConfigLibraryService}:} the business service that validates payloads, prevents
    duplicate names, and performs CRUD operations.
    \item \textbf{\texttt{ConfigLibraryController}:} the REST controller that exposes the library API to
    the frontend.
\end{itemize}

\paragraph{}Figure~\ref{fig:ch7-library-sequence} shows the main sequence interactions of the configuration

locally on the frontend. Loading applies compatibility checks before opening the corresponding
generation screen, and update or delete actions use the same API layer to keep the displayed
library synchronized with the SQLite state.

standalone and connected configurations do not have exactly the same shape. Instead of creating many

as text and validates that it is syntactically valid JSON before saving it.

\subsection{Compatibility Rules}

\paragraph{}Standalone configurations can be loaded directly into standalone mode because they do not
depend on external database state. Connected configurations require stronger checks. A connected
configuration saved for an accounts-only workflow is not necessarily valid in a securities-only
workflow, and a configuration that generates securities should not be loaded when securities are
already grabbed from the database. For this reason, connected configurations are saved with their
\texttt{grabMode}, and the frontend applies compatibility rules before enabling the load action.

\paragraph{}The compatibility rules prevent the user from creating incoherent scenarios such as enabling
executions without orders, generating accounts when explicit accounts were already grabbed, or
generating dependent trading records without both accounts and securities being available.

\paragraph{}The \texttt{ConfigLibraryService} validates every create request. A configuration must have a
non-empty name, a valid mode, valid JSON content, and a valid connected grab mode when the mode is
\texttt{connected}. Standalone configurations are rejected if they include a connected grab mode. The
service also rejects duplicate names using a case-insensitive lookup.

\subsection{Frontend Library Page}

\paragraph{}The frontend implements a dedicated \texttt{ConfigLibrary} page available at \texttt{/library} and
also contextually from the standalone and connected workflows. The page displays saved
configurations with their mode badge, name, optional description, and creation date. Users can
search by name or mode, filter by \texttt{All}, \texttt{Standalone}, or \texttt{Connected}, and navigate
large libraries through pagination.

\paragraph{}The page also supports inline renaming and guarded deletion. Renaming checks for duplicate names
on the frontend before calling the backend, while deletion uses a confirmation dialog to prevent
accidental removal. When the backend is unavailable, the page displays an error state with a retry
action.

\subsection{Standalone Library Integration}

\paragraph{}Standalone configurations are saved from the standalone generation workflow and loaded back into
the standalone configuration page. The frontend merges saved JSON with current default values before
loading it. This protects the application from older saved configurations that may not contain newer
fields added later in development.

\subsection{Connected Library Integration}

\paragraph{}Connected configurations are more context-sensitive. The connected workflow can save a
configuration only after a grab mode has been detected. The saved payload contains the reference
date and generation sections for accounts, securities, prices, positions, proposed orders, group
orders, models, and executions, along with the detected \texttt{grabMode}.

\paragraph{}When loading a connected configuration, the frontend first checks whether the current grabbed
data is compatible with the saved configuration. If the configuration cannot be used in the current
context, the load button is disabled and an explanation is shown. This avoids silent misconfiguration
and guides the user back toward a coherent generation scenario.

\subsection{Local Frontend Persistence and Routing}

\paragraph{}The application also uses local storage hooks to preserve in-progress form state during a
browser session. Separate hooks manage standalone configuration, connected configuration, connection
state, and grabbed data. Grabbed data is keyed by the current server and database name so that
changing the connection resets stale selections.

\paragraph{}Routing was finalized in \texttt{App.tsx}. The application now contains a mode selection page,
standalone routes, connected routes, and a shared library route. Connected mode also includes
disconnect confirmation when the user attempts to leave an active database session, preventing the
frontend from keeping a misleading connected state after navigation.

\section{Sprint Review}
% ─────────────────────────────────────────────


\paragraph{}At the end of Sprint 5, the application had evolved from a technical generator into a complete
tool usable by QA engineers. The configuration library improved reproducibility by allowing common
scenarios to be saved and reused. The connected compatibility logic reduced the risk of invalid
generation requests, while final routing and state management made the user workflow more stable.

\paragraph{}The main limitation that remains is that connected mode depends on the availability and structure
of a Longview SQL Server environment. The implementation includes flexible mapping and safe
fallbacks for optional fields, but deeper validation against all possible client-specific schema
customizations would require broader testing across several Longview environments.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
% ─────────────────────────────────────────────


\paragraph{}This chapter presented Sprint 5, which finalized the Longview Test Data Generator by adding a
SQLite-backed configuration library and completing the application workflows. The backend now
persists named standalone and connected configurations through TypeORM, while the frontend provides
a searchable and filterable library page with load, rename, and delete actions. Connected
configuration loading is protected by compatibility rules that account for the currently grabbed
database data. With this sprint, the system became a complete full-stack tool covering data
generation, database anchoring, AI enrichment, validation, SQL export, and scenario reuse.
